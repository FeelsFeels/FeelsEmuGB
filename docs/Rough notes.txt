On the memory map:
The GB has a 16-bit address space, 0x0000 - 0xFFFF

0000	3FFF	16 KiB: Cartridge. Fixed Bank
4000	7FFF	16 KiB: Cartridge. Switchable ROM Bank. We access "extra memory" in the cartridge (Pokémon red is 512KB!) in this address range via the Memory Bank Controller (MBC).
8000	9FFF	 8 KiB: Video RAM. Tile Data, Tile Maps. Important for the PPU.
A000	BFFF	 8 KiB: External RAM. This lives on the cartridge. I think this is where the save files can live.
C000	DFFF	 8 KiB: Work RAM.
E000	FDFF this section is broken. It's a mirror of C000-DDFF. Just don't use this, or redirect to the work RAM.
FE00	FE9F	     : Object Attribute Memory (OAM). Holds up to 40 sprites.
FEA0	FEFF	Not Usable
FF00	FF7F	     : I/O Registers
FF80	FFFE	     : High RAM (HRAM). 127 bytes of RAM that can be accessed faster (similar to CPU cache)
FFFF	FFFF	Interrupt Enable register (IE)


On the Memory Bank Controller (MBC):
https://retrocomputing.stackexchange.com/questions/11732/how-does-the-gameboys-memory-bank-switching-work

The general concept is you write to ranges to switch which memory bank you are reading from. 
Since the gameboy can only read from a 16-bit address space, this allows you to read from more memory than the address space allows.

On MBC1:
0x0000-0x3FFF - Read only, cannot switch nor modify.
0x4000-0x7FFF - Read only. Contains whatever memory bank is currently being selected.
0xA000-0xBFFF - Read/Write. This is where the RAM bank lives, if present. Can have multiple banks as well.

Writes to control:
0x0000-0x1FFF - Writing to this range enables/disables RAM. Write the value 0x0A to anywhere in this range to enable. Any other value disables it.
0x2000-0x3FFF - Writing to this range switches the ROM Bank. Only the bottom 5 bits are taken into account.
                Writing 0xE1 (111 00001) will select rom bank 01. IMPORTANT CONCEPT: If set to 0, it behaves as if it was set to bank 01.
                If the number of rom banks need only, say, 4 bits to represent, the 5th bit is masked, which ignores it for bank selection.
                  Even so, 0b10000 is considered different from 0b00000, so you can map bank 0 on smaller Cartridges this way.
                
0x4000-0x5FFF - Larger carts needing >5bits bank numbers, there is a second banking register located here, which supplies 2 additional bits for the bank number.
                Final computation: Selected ROM Bank = (Secondary Bank << 5) + Primary ROM Bank
                Weird behaviour: these two extra bits are not taken into account for the bank 00 -> 01 translation as described above.
                Thus, accessing bank 0x20, 0x40, and 0x60 selects bank 0x21, 0x41, and 0x61 instead.
                This 2 bit register can also be used to select the RAM Bank, depending on the ROM/RAM selection mode(below).

0x6000-0x7FFF - 1 bit register representing Banking Mode select. Controls the behaviour of the Secondary 2 bit bank selection register.
                0: Simple(default). 0x0000-0x3FFF for ROM and 0xA000-0xBFFF for RAM is locked to bank 0 of ROM and SRAM.
                1: Advanced. 0x0000-0x3FFF and 0xA000-0xBFFF can now be switched via the second banking register.

The CPU has registers, but the docs also mention the cartridge having registers.
The registers of the cartridge are better thought of as control switches than the standard definition of registers on the CPU.

On CPU Registers:
7 General 8-bit registers: A B C D E H L
Some registers can be combined to make 16 bit registers: AF, BC, DE, HL
A refers to Hi bits of AF. F is the flags register.
A register is special. It is the accumulator. The only register that can be used for certain load instructions.
HL register is usually the only register that can be used for addresses when accessing memory.

Two more registers, SP & PC, for stack and program pointer.

On the Boot ROM:
Exists in 0000-00FF. Recall that the entry point of the cartridge is 0100-0103.
This small program, the boot ROM, is burned inside the CPU, and is mapped over (overlapped) the cartridge ROM on startup.
This means that the boot ROM supercedes the cartridge code inside 0000-00FF until it finishes.
After finishing, the boot ROM hands off control to the cartridge at 0x0100.

Timer registers:
*UINT16_T* div { 0 };	// Divider. For the software, increments at a rate of rate of 16384Hz(once every 256 T-cycles). This is your "true" counter of how many cycles have passed
uint8_t tima{ 0 };	    // Timer counter. Increments at TAC frequency.

DIV, to the software, appears as an 8-bit register incremented every 256 cycles. However, internally, the DIV is a 16-bit register incremented every T-Cycle.
TIMA, on overflow, triggers a hardware TIMER interrupt.
TIMA ticks on falling edge, that is, when the target bit on DIV(target controlled in tac), goes from 1 -> 0, tima increments.

On Graphics:
VRAM Structure:
Tile Data - stored in 0x8000-0x97FF, in two "blocks" or "addressing modes".
  0x8000-0x8FFF / 0x8800-0x97FF
Tile Maps - stored in 0x9800-0x9FFF. Two blocks of 32x32 grids(0x9800-0x9BFF and 0x9C00-0x9FFF). This is "Which tiles to display where"

https://www.huderlem.com/demos/gameboy2bpp.html
Each tile is 16 bytes. Thus 384 tiles. Stored in three "blocks" of 128 tiles each
Each tile is 8x8 pixels.
Each line is represented by 2 bytes. (8 lines)
Each pixel has 2 bits of color depth, 4 colors (grey shades)
Example of a tile:
FF 00 7E FF 85 81 89 83 93 85 A5 8B C9 97 7E FF
0xFF 0x00 represents the 1st row, 0x7E 0xFF represents the second, and so on.
Each pixel can have 4 colors (or more accurately said to be shades of grey) - 00, 01, 10, 11.
You get these colors by combining the bits of the high byte and low byte of the tile info.
For example, the second line: 7E (low byte) FF (high byte)
1111 1111
0111 1110
for the first pixel, we combine the high and low bytes to get a pixel color of 10 (color 3)
for the second pixel, 11. These two bits are what is called "color index", for the OAM priority later.

Background:
The Gameboy screen is only 160x144. but the background is a 256x256 map (32 tiles * 8 pixels = 256). 
Tiles only contain references to the tiles in VRAM.
But each tile in the map can only store values of 0-255, while VRAM can store 384 tiles.
There is an additional setting in lcdc, ""BG & Window tiles", bit 4, which controls which "half" you are referencing.
0 being 0x8800-0x97FF, and 1 being 0x8000-0x8FFF in vram. Note the overlap! 0x8800-0x8FFF is overlapped! A 128 tile overlap.

Background can also be scrolled via scy and scx registers. These two registers specify which part of the 256x256 background is visible.
If values are larger than 255, like in the case of when scx = 40, (40 + 159) = 199, they loop around the screen.

The tilemap the background uses is specified at bit 3 of LCDC. 0 uses the tilemap at 0x9800, otherwise the 0x9C00 one.
Window has the same tilemap choosing behaviour, at bit 6 of LCDC.
The bytes in the tilemap is just an index pointing to the tile data.

Window:
wy and wx specify the Window's top-left pixel, but wx is + 7. namely wx=7, wy=0 is top left.
Windows are frequently used for immovable ui, like healthbar at the bottom of kirby.


OAM (object attribute map/memory) - think of these as objects / sprites
Controlled through 0xFF40 bit 1 and 2. Bit 1 enables/disables. Bit 2 controls size: 0 = 8x8, 1 = 8 x 16.

An object, an entry in OAM, is composed of 1 or 2 tiles(8x8 or 8x16 pixels). Can be moved independently of the background.
Limitation of hardware allows only 10 objects per scanline (row). Objects out of the screen, within the 256x256 BG map still contributes to the limitation.

Each object has an OAM Entry consisting of 4 bytes - Y Pos, X Pos, Tile Index, and Attributes. Stored in 0xFE00-0xFE9F
Positions are (0,0) at the top left. Objects anchored/origin at top right.
Position Y - for BOTH 8x8 and 8x16 sprites, 0x10(16 in decimal) will have its top border touching the top edge of the screen.
Position X - for a 8x8 sprite the "anchor is on the right". Meaning 0x00 will have it's right border at the leftmost edge of the screen. 
             0x04 is half cut off, 0x08 has left border touching leftmost edge.
Tile Index - in 8x8 mode, specifies tile index in vram. this means that only tiles from 0x8000-0x8FFF can be selected.
             in 8x16 mode, byte1 is top tile, byte2, the one that follows right after, is the bottom tile of the sprite.
CGB Palette, Bank: cgb mode only. im not supporting yet
DMG Palette - 0 uses OBP0, 0xFF48, 1 uses OBP1, 0xFF49
Flip X - Self explanatory
Flip Y - Self explanatory
Priority - if 1, BG and Window color indices 1-3 are drawn over this sprite.



On Palettes:
Remember the fact that the gameboy has 4 colors (color indexes) - 00, 01, 10, 11, with the colors being White, Light gray, Dark grey, and Black respectively
Each pixel has a ColorID as well - 0, 1, 2, 3.
The palettes remap the ColorID to these 4 color indexes.
There are two types of palletes - Background palette data, and OBJ palette data. What both of them do is self explanatory. It's just bg vs obj.
But note that the color index 0 is ignored for OBJ since 0 is transparent for OBJs. There are also two OBJ palettes. One at 0xFF48 and one at 0xFF49.
Each object chooses which palette to use from it's OAM entry (see above, "DMG Palette").


Deeper understanding of the clock.
The Master clock runs at 4.194304Mhz. So 4,194,304 cycles per second. This is in T-Cycles.
T-Cycles are the smallest unit of measurable time.
M-Cycles are the useful units of time. In the gameboy's case, 4 T cycles -> 1 M cycle.

Timing for graphics:
GB resolution: 160 x 144
Dots are same as cycles, one 4.194 Mhz time unit. 1 Dot = 1/4,194,304 second
A frame consists of 154 scanlines (rows).
The gameboy's screen height is 144 pixels, and the PPU also defines a 10 extra scanline duration as it's V-blank (144 + 10) = 154 scanlines
One scanline is drawn in 456 dots, so total times taken for one frame is 456 x 154 = 70244 dots.
This 456 value is computed as such:
Each scanline is drawn in 3 phases - OAM retrival (always 80 dots), Drawing(172-289 dots), H-Blank(87-204 dots).
The H blank actual duration seems to be 87, but will compensate and take extra time depending on how fast the drawing stage took, 
leading to a consistent 456 dot timing for one scanline.

To be exact, the drawing is controlled by this thing called Pixel FIFO.
PPU holds 16 pixels at once to be drawn in a queue.
The ppu draws one pixel per screen per clock, and pauses unless it contains more than 8 pixels.
When fetching more pixels, 3 clocks are needed + 1 idle clock.

On Interrupts:
3 main parts that control the interrupt system.
IF register 0xFF0F - The state of the interrupts. "Do I need to handle any interrupts?"
IE register 0xFFFF - Interrupt table. Enables/Disables whether each interrupt can be called.
IME flag, internal to cpu - Enables/Disables all interrupts globally.


0xFF41: STAT register for graphics is a weird one.
Bit 7: Unused.
Bit 6: LYC=LY Interrupt Enable (1=enabled)
Bit 5: Mode 2 (OAM Search) Interrupt Enable (1=enabled)
Bit 4: Mode 1 (VBlank) Interrupt Enable (1=enabled)
Bit 3: Mode 0 (HBlank) Interrupt Enable (1=enabled)
Bit 2: LYC=LY Flag (1=LY matches LYC, read-only)
Bit 1-0: PPU Mode (read-only)
  00 = Mode 0 (HBlank)
  01 = Mode 1 (VBlank)
  10 = Mode 2 (OAM Search)
  11 = Mode 3 (Drawing)

Common Terminology:
DAC - Digital to Analog Converter. Converts binary data to electrical voltage. The electricity then vibrates the speaker to produce sound.
Amplitude - How high a wave goes. Volume.
Frequency - How fast the wave repeats. How many cycles/time. High frequency = higher pitch



4 different channels. There is a secret 5th VIN channel inside cartridges that is unused.
2 Pulse Channels (producing Square Waves), 1 Wave, 1 Noise.
Think about each channel as an instrument, all playing at the same time.
In this regard, the GB's audio system is more of a synthesizer.
Each channel produces a wave, which you produce an audio sample from.

3 "Master control" registers.
0xFF26/NR52 - APU enable/disable
0xFF25/NR51 - Sound panning
0xFF24/NR50 - Volume control

In general, all 4 different types of channels have 5 registers(1 byte) for each of them.
Going by pandocs notation system, NRxy, where x is the channel number, and y is the registers for each of the channels. x=5 is for global controls
These registers control (in general):
NRx0: specific channel behaviour (Pulse A has sweep)
NRx1: Length timer
NRx2: Volume and Envelope(how sound changes over time) control
NRx3: Frequency/Period
NRx4: Control(on/off), Timers, and extra frequency bits.

0xFF26: The audio master Register
Bit 7  : Audio on/off
Bit 6-4: Unused
Bit 3-0: Read only. This is a check for whether audio channels 4-1 is on. (QUESTION: I asssume 1 is on? Or is it like input where 0 is on?)

0xFF25: Sound panning.
The Game Boy has binary sound panning. If you have Stereo sound, sound has the ability to come out only in the left ear or right ear.
To hear sound only in the left ear, set Left bit to 1, and Right bit to 0.
For centered sound, set both bits to 1.

Bit 7-4: Left panning for channels 4-1
Bit 3-0: Right panning for channels 4-1

0xFF24: Master Volume control, VIN panning.
VIN stands for Voltage Input. In the context of the Game Boy, it refers to External Sound Input. Set to 0 if external sound is not being used.
For volume control, value of 0 is very quiet, value of 7 is loudest.
Bit 7  : VIN left
Bit 6-4: Volume left
Bit 3  : VIN right
Bit 2-0: Volume right


Overview of what kind of sounds the four channels make:
Pulse 1 and 2 - The Square Waveforms
A square wave is a sound wave with only two distinct amplitudes, up and down.
Rapidly switches a voltage between High and Low. 
There are only four distinct, predetermined waveforms you can use, controlled by the 2 Duty cycle bits.
12.5%, 25%, 50%, 75%. There is no audible difference between 25% and 75%.
For example, a 50% waveform and 25% might look like this:
High      ________                      High      ____
         |        |                              |    |
Low    __|        |________ repeating   Low    __|    |______   repeating
The sample sound made is 0 when down, and the amplitude is controllable by volume bits when up.
Pulse 1 has a sweep channel. This sweep is extra control for frequency.

Wave channel
Has 16 bytes of Wave RAM. Each byte holds two samples, each 4 bits(15 values).
Unlike the Square Waveforms which only allow you to control frequency and amplitude, this wave RAM allows you to control the shape as well.
Value
 15 |      __
    |    /    \
    |   /      \
  0 |__/________\__
    (32 samples of custom data)
To better understand frequency, think of it as how fast this wave table above is being played.
Frequency has nothing to do with the shape of the wave.


Important thing to understand:
> The registers hold data, but the audio sample is produced from an internal state.
The internal state is modified via Ticking the APU. The registers, instead of storing audio data,
is closer to storing the settings for the audio data, or controlling it.

> Also important is the idea of triggering. From pandocs, talking about NR12 (volume and envelope):
  | Writes to this register while the channel is on require retriggering it afterwards. 
  | If the write turns the channel off, retriggering is not necessary (it would do nothing).
This means a game developer is supposed to set the state, trigger the channel, and then let it do it's thing.
This means that we need to keep track of the internal state, like initial volume.
BUT, Referencing SameBoy, only the initial volume state is saved.

Timing the APU:
Reminder that the CPU runs at 4194304Hz.
Inside the APU, there are two different "Timers".
The first is the lower frequency DIV-APU. I believe it's also called a frame sequencer?
The second is the high frequency timer that handles the audio waveform generation. Things like the period clocks in CH1/3, once every 4/2 dots.

"A “DIV-APU” counter is increased every time DIV’s bit 4 goes from 1 to 0, therefore at a frequency of 512 Hz."
So, the DIV-APU ticks when the 12th bit in the 16-bit div register's falling edge is triggered.
Meaning the DIV-APU ticks every 8192 T-Cycles.
4194304 / 2^13 = 4194304 / 8192 = 512Hz

Furthermore, there are events triggered every N DIV-APU ticks, described in the table below.
Step, Sound Length, CH1 sweep, Envelope Sweep
0,    Tick,         ----,      ----
1,    ----,         ----,      ----
2,    Tick,         Tick,      ----
3,    ----,         ----,      ----
4,    Tick          ----,      ----
5,    ----,         ----,      ----
6,    Tick          Tick,      Tick
7,    ----,         ----,      ----


Imagine the two clocks running parallel in time:
The High-Frequency Oscillator (runs extremely fast):
- Counts down timerCycles.
- Hits 0! Advances the duty pointer (flips the speaker).
- Looks at the current shadowFrequency.
- Reloads timerCycles = (2048 - shadowFrequency) * 4.
- Repeats hundreds of times.

The Frame Sequencer (runs extremely slow):
- Wakes up once every 8192 T-Cycles.
- The Sweep math calculates a new pitch.
- It overwrites shadowFrequency with the new pitch.
- It instantly overwrites the current timerCycles countdown so the pitch bend takes effect immediately instead of waiting for the current cycle to finish.

Shitty summary
Phase 1: The Blueprint (Memory & Registers)
The NRxx registers (0xFF10 to 0xFF3F) are simply the control dials on the front of the factory.
When the Game Boy CPU executes an instruction that writes to memory, it is turning these dials.
Crucial Concept: Turning a dial usually does absolutely nothing to the active sound. It just updates the blueprint for the next time the machine is turned on.

Phase 2: The Spark (The Trigger Event)
The entire factory sits idle until the CPU writes a 1 to Bit 7 of NRx4. 
This is the big red "START" button. When this happens, the APU executes a Trigger Event.
It forcefully reads all the dials (the Blueprint) and copies those values deep into the machine's internal memory (the Engine).
It resets the internal timers, reloads the lengths, and flips channelEnabled = true. The factory roars to life.

Phase 3: The Dual-Clock Engine
Once the channel is enabled, it is governed by two completely separate clocks running in parallel. 
This is the heart of your APU::Tick(int cycles) function.
    Clock A: The Conductor (The Frame Sequencer)
Speed: Very slow (512 Hz, or exactly once every 8,192 T-Cycles).
Job: To handle the musicality of the sound. It does not generate audio waves; it shapes them over time.
Flow: It steps through an 8-step sequence.
On certain steps, it tells the Length Counter to tick down. (If it hits 0, it hits the kill switch: channelEnabled = false).
On certain steps, it tells the Volume Envelope to tick down. (If it hits 0, it nudges the internal currentVolume up or down by 1).
On certain steps, it tells the Sweep to calculate a new pitch. (If applied, it dynamically overwrites the shadowFrequency and instantly updates the Oscillator).
    Clock B: The Musicians (The Oscillators)
Speed: Extremely fast (Up to 1,048,576 Hz).
Job: To generate the raw physical sound waves.
Flow: Each channel has a frequencyTimer countdown variable. 
Every single CPU T-Cycle, this timer drops.
When frequencyTimer hits 0, the channel takes exactly one step forward in its physical waveform.
Square (Ch 1 & 2): It moves the dutyPointer by 1, outputting either high or low voltage based on the 8-step pattern.
Wave (Ch 3): It moves the wavePosition by 1, outputting the specific 4-bit sample from Wave RAM.
Noise (Ch 4): It shifts the 15-bit LFSR by 1, outputting static based on the new Bit 0.

Phase 4: The Output (The Mixer)
The APU Engine is completely disconnected from your PC's speakers. It just runs in the background, furiously flipping duty pointers and shifting volumes.
Enter the Mixer.
Speed: Matches your PC audio (44,100 Hz, or roughly once every 95 T-Cycles).
Job: To take a "photograph" of the factory.
Flow: Every 95 T-Cycles, the Mixer walks up to the 4 channels and asks, "What is your exact amplitude right now?"
If Channel 1's channelEnabled is true, its dutyPointer is currently on a 1, and its currentVolume is 12, it hands the Mixer the number 12.
If it's on a 0, or the channel is disabled, it hands the Mixer a 0.
The Mixer takes these numbers from all four channels, adds them together, 
applies panning (left/right audio via NR51), applies master volume (NR50), and pushes the final floating-point number to SDL_QueueAudio().

The Summary Flowchart
CPU Writes to NRxx -> Updates the Blueprint.
CPU Writes to NRx4 (Bit 7) -> Triggers the Engine -> channelEnabled = true.
Every CPU Cycle:High-Freq Clock ticks -> Advances waveform step -> Outputs an active value (0 to 15).
Low-Freq Clock ticks (every 8192 cycles) -> Shapes the volume/pitch/duration.
Every 95 CPU Cycles:Mixer samples the active value -> Sends to SDL -> You hear sound.
